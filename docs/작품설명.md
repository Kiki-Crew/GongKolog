# 1. 작품 설명 — GongKolog(공고로그)

---

## 가. 작품 개요

### 1) 개발 목표

**GongKolog(공고로그)** 는 채용공고와 자기소개서를 **의미 단위로 맞대어**, 지원자의 답변이
공고가 요구하는 바를 **얼마나 충족하는지**를 자동으로 진단하는 AI 자소서 점검 서비스이다.

취업 준비생은 자기소개서를 채용공고의 인재상과 직무 요구에 맞춰 작성해야 하지만, 정작
자신의 답변이 공고가 원하는 요소를 담고 있는지 **객관적으로 점검하기 어렵다.** 기존의 AI
첨삭(예: 생성형 챗봇에 자소서를 통째로 입력)은 "전반적으로 잘 썼다 / 더 구체적으로 써라"
수준의 **두루뭉술한 피드백**에 그쳐, *무엇이 충족됐고 무엇이 빠졌는지*를 항목 단위로
짚어주지 못한다. 또한 단순 키워드 매칭 도구는 단어의 표면적 일치만 확인할 뿐, "팀 프로젝트에
참여했다"가 곧 "리더십을 보여준다"는 아니라는 **의미의 차이**를 구분하지 못한다.

본 작품의 개발 목표는 다음과 같다.

- 자소서 문항과 채용공고를 함께 해석하여, 그 답변이 충족해야 할 **평가 카테고리를 자동 도출**한다.
- 각 카테고리에 대해 답변을 **충족 / 약함 / 공백(3색)** 으로 판정하고, 부족한 부분에 **구체적 보완
  제안**을 제시한다.
- 키워드가 아니라 **의미(임베딩 + LLM)** 로 판정하여, 표면적 단어 일치가 아닌 실질적 충족 여부를
  평가한다.
- 지원자가 제출 전에 자신의 자소서에서 **빠진 부분을 시각적으로 확인하고 스스로 보완**하도록 돕는다.

### 2) 개발 개요

본 서비스는 **웹 애플리케이션** 형태로 구현되었으며, 사용자는 브라우저에서 채용공고와 여러 개의
자소서 문항(질문+답변)을 입력하고 즉시 진단 결과를 받아볼 수 있다. 로그인 없이도 분석이
가능하며, 로그인(Google 계정) 시 분석 결과와 자소서·공고를 저장하고 다시 불러올 수 있다.

핵심은 **"임베딩으로 후보를 좁히고 LLM으로 판정하는 2단계 구조"** 이다. 채용공고 전체를 그대로
LLM에 넣는 대신, ① 문항+공고에서 평가 카테고리를 추출하고 ② 임베딩으로 답변에서 관련 근거를
찾아 후보를 압축한 뒤 ③ LLM이 카테고리별로 판정하게 함으로써, 누락 없이 항목별로 정밀하게
평가한다.

### 3) 대상 사용자

- 채용에 지원하는 **취업 준비생·이직 준비자**
- 자소서를 여러 번 수정하며 공고별로 맞춤화하려는 지원자
- 제출 전 자소서의 완성도를 객관적으로 점검하고 싶은 사용자

### 4) 핵심 차별점

| 구분 | 기존 방식 | GongKolog |
|---|---|---|
| 분석 단위 | 자소서 전체를 통째로 입력 | **문항별 + 공고 통합**으로 평가 카테고리 도출 |
| 판정 방식 | 두루뭉술한 총평 | **충족/약함/공백 3색** 항목별 판정 |
| 매칭 방식 | 키워드 표면 일치 | **의미 기반**(임베딩 + LLM 추론) |
| 결과 활용 | "고쳐라" 수준 | **빠진 항목 + 구체적 보완 제안** 제시 |
| 안정성 | 단일 모델 | **멀티 LLM 역할 분담 + 폴백 + 재시도** |
| 개인정보 | — | **비로그인 분석은 즉시 폐기** |

## 나. 시스템 구성도

시스템 구성도는 `docs/architecture.png` 참조. 주요 흐름은 다음과 같다.

1. **인증은 프론트엔드 ↔ Supabase Auth 직통**(Google OAuth)으로 처리하여 토큰(JWT)을 수령한다.
2. **모든 데이터 처리는 FastAPI 백엔드를 경유**한다(프론트가 DB에 직접 접근하지 않음).
3. 백엔드는 요청의 JWT를 **JWKS(공개키)** 로 검증하여 사용자 신원을 확인한다.
4. 분석 엔진은 **① 카테고리 추출 → ② 문장 분리 → ③ 임베딩 후보 검색 → ④ 충족 판정 →
   ⑤ 결과 조립**의 5단계 파이프라인으로 동작한다.
5. LLM 호출은 **Groq API**(추출: Llama-3.3-70B, 판정: GPT-OSS-120B)를 사용하며 상호 폴백한다.
6. 결과는 **Supabase PostgreSQL**에 저장(로그인 사용자)되고, 응답 JSON이 프론트로 전달되어
   3색으로 시각화된다.

> *(그림 삽입 위치) `docs/architecture.png` — 시스템 구성도*

## 다. 구현 기능

### 1. 분석 엔진 — 2단계 의미 매칭 (핵심 기능)

분석 엔진은 본 작품의 심장으로, 하나의 문항(질문+답변)과 공통 채용공고를 입력받아
카테고리별 충족 판정을 산출한다. 문항이 여러 개이면 각 문항을 독립적으로 분석한 뒤 전체 요약을
집계한다.

#### 1.1 평가 카테고리 추출 (1단계)

자소서 문항과 채용공고를 함께 LLM(Llama-3.3-70B)에 전달하여, 그 답변이 충족해야 할 핵심
**평가 카테고리 2~3개**를 도출한다. 이때 다음 원칙을 적용한다.

- 문항이 직접 묻는 내용을 최우선으로 하고, 공고는 문항 해석을 돕는 보조 자료로 사용한다.
- 첫 번째 카테고리는 **경험 근거의 충실성**(본인 역할·수행 과정·산출물·결과), 두 번째 카테고리는
  **직무 적용 가능성**으로 관점을 분리하여, 두 기준이 같은 근거를 중복 요구하지 않게 한다.
- 세부 기술명·자격증명은 독립 카테고리로 만들지 않고, 넓은 역량 카테고리 안의 근거로만 반영한다.
- 각 카테고리에는 판정을 돕는 **`job_signals`(공고의 핵심 업무·역량 신호)** 를 함께 생성한다.

각 카테고리는 `category`(이름), `criteria`(충족 기준 한 문장), `from`(출처: 문항/공고),
`job_signals`로 구성된다.

#### 1.2 한국어 문장 분리 (2단계)

자소서 답변을 한국어 형태소 기반 문장 분리기(**KSS**)로 분리하고 각 문장에 `s1, s2, …`
식별자를 부여한다. 이 식별자는 이후 결과 화면에서 **근거 문장을 하이라이트할 좌표**로 사용된다.
텍스트가 아니라 id로 연결하므로 띄어쓰기·중복으로 인한 매칭 오류가 발생하지 않는다.

#### 1.3 임베딩 기반 다관점 후보 검색 (3단계)

한국어 특화 임베딩 모델 **BGE-M3**(sentence-transformers)로 카테고리와 답변 문장을 벡터화하고
코사인 유사도로 관련 근거를 찾는다. 본 단계는 단순 top-k 검색을 넘어 다음과 같이 고도화되었다.

- **다관점 질의 확장**: 하나의 카테고리를 `상황·문제의식`, `본인 행동·판단`, `방법·자료 활용`,
  `결과·배운 점·적용 방향` 등 여러 관점의 검색 질문으로 확장한다. 각 후보가 어떤 관점에서 뽑혔는지
  **역할(role)** 을 함께 보존하여, 판정 단계에서 LLM이 사람 평가자처럼 구조적으로 읽을 수 있게 한다.
- **문장 윈도우**: 인접한 2개 문장을 하나의 검색 단위(윈도우)로 묶는다. 자소서는 한 문장으로 의미가
  완결되지 않는 경우가 많아(방법은 앞 문장, 결과는 뒷 문장), 흐름을 보존하기 위함이다.
- **중복 억제**: 이미 선택된 근거와 문장 id가 과반 이상 겹치면 제외하여, 서로 다른 관점의 다양한
  근거를 확보한다.

> 자소서 문장은 수십 개 수준이므로 벡터DB 없이 **NumPy 행렬 연산**만으로 충분히 처리된다.

#### 1.4 LLM 충족 판정 (4단계)

3단계에서 좁혀진 후보 근거를 LLM(GPT-OSS-120B)에 전달하여 각 카테고리를 판정한다. 판정 결과는
`met`(충족), `weak`(약함), `missing`(공백) 세 가지이며, 판정 이유(`comment`)와 보완
제안(`suggestion`)을 함께 산출한다. 판정 프롬프트는 다음을 반영한다.

- **met**: 카테고리 핵심에 직접 답하고, 경험·행동·방법·결과·직무 연결 중 필요한 요소가 충분히 이어질 때.
- **weak**: 관련 근거는 있으나 핵심 요소가 일부 부족하거나 직무 연결이 추상적일 때.
- **missing**: 연결할 만한 답변 근거가 거의 없을 때.
- 표면적 단어 일치는 충족이 아니며(예: "팀 프로젝트 참여" ≠ "리더십"), 정량 성과·주도성 표현은
  기준에 부합할 때 근거로 인정한다. 확신이 서지 않으면 보수적으로 weak로 판정한다.
- 답변에 없는 사실·수치·역할을 만들어내지 않으며, 근거가 된 실제 문장 id만 `evidence_ids`에 담는다.

#### 1.5 결과 조립 및 응답 스키마 (5단계)

추출 결과와 판정 결과를 문항별로 병합하고 전체 요약을 집계한다. LLM이 빈 응답이나 형식이 어긋난
값을 반환해도, 조립 단계에서 **상태 규칙 불변식**(met은 suggestion 없음 / weak·missing은
suggestion 존재 / missing은 evidence 없음)을 강제하여 화면이 깨지지 않도록 방어한다.

응답 JSON은 다음 구조를 갖는다.

```json
{
  "analysis_id": "uuid",
  "overall_summary": { "total_items": 2, "total_categories": 6,
                       "met": 3, "weak": 2, "missing": 1, "coverage_score": 0.5 },
  "items": [
    {
      "item_id": "i1",
      "question": "협업에서 중요한 요소와 사례는?",
      "answer_sentences": [ { "id": "s1", "text": "..." } ],
      "summary": { "total": 3, "met": 2, "weak": 1, "missing": 0 },
      "categories": [
        { "id": "c1", "category": "협업 가치관 및 실행력",
          "from": ["문항","공고"], "criteria": "...",
          "status": "met", "evidence_ids": ["s2"],
          "comment": "...", "suggestion": null }
      ]
    }
  ]
}
```

#### 1.6 멀티 LLM 역할 분담 + 폴백 + 재시도 (안정성 설계)

- **역할 분담**: 추출은 Llama-3.3-70B, 판정은 GPT-OSS-120B가 담당한다(둘 다 Groq API 서빙).
- **폴백**: 한 모델 호출이 실패하면 다른 모델로 자동 전환하여 재시도한다.
- **일시 오류 재시도**: 503(과부하)·타임아웃 등 일시적 오류에는 짧은 지연 후 자동 재시도한다.
- **JSON 방어**: 모델이 배열 대신 객체로 감싸 반환하거나(예: `{"result":[...]}`) 파싱에 실패해도
  내부 리스트를 추출하고 1회 재시도한다.

> *(그림 삽입 위치) 분석 파이프라인 흐름도 또는 코드 구조 스크린샷*

### 2. 진단 결과 시각화 (3색 결과 화면)

분석 결과는 문항별 패널로 시각화된다.

- **상단 전체 요약**: "문항 N개 · 카테고리 M개 중 🟢충족 / 🟡약함 / 🔴공백" 및 커버리지 비율.
- **문항별 패널(아코디언)**: 각 문항을 접고 펼 수 있으며, 헤더에 해당 문항의 3색 집계를 표시한다.
- **좌: 답변 본문 / 우: 평가 카테고리** 2단 구성.
- 각 카테고리 카드는 **status에 따른 색(🟢🟡🔴)**, **출처 배지(문항/공고)**, 충족 기준(criteria),
  판정 코멘트, 보완 제안(💡)을 보여준다.
- 카테고리를 클릭하면 그 판정의 **근거가 된 답변 문장이 하이라이트**된다(같은 문항 범위 안에서만).

> *(그림 삽입 위치) 결과 화면 전체 / 카테고리 클릭 시 근거 하이라이트 스크린샷 2장*

### 3. 회원 / 인증 (Google OAuth)

- Supabase Auth의 Google 프로바이더를 사용하여 소셜 로그인을 구현하였다(자체 비밀번호 관리 없음).
- 프론트엔드는 Supabase와 직접 통신해 로그인하고 세션(JWT)을 수령한다.
- 이후 모든 백엔드 API 요청에는 Axios 인터셉터가 **JWT를 자동으로 헤더에 첨부**한다.
- 백엔드는 토큰의 서명 방식(HS256 또는 비대칭 RS/ES256)을 자동 판별하여, 필요 시 Supabase의
  **JWKS(공개키)** 로 서명을 검증하고 사용자 id를 추출한다.

> *(그림 삽입 위치) 로그인 화면 / Google 로그인 버튼 스크린샷*

---

### 4. 분석 결과 저장 · 공유

- 로그인 사용자의 분석 결과는 `analyses` 테이블에 **응답 JSON을 통째로(jsonb) 저장**한다.
- 저장된 결과는 `analysis_id`로 다시 조회할 수 있으며, **공유 링크(`/share/:id`)** 를 통해
  로그인 없이도 열람 가능하다(결과 화면에 "공유 링크 복사" 버튼 제공).
- **비로그인 분석은 저장하지 않고 즉시 폐기**하여 개인정보를 보호한다. 이 경우 결과는 그 화면에서만
  확인되고 새로고침 시 사라지며, 안내 문구로 이를 명시한다.

> *(그림 삽입 위치) 공유 링크 복사 / 공유 결과 열람 화면 스크린샷*

### 5. 마이페이지 (자소서 · 공고 관리)

- **내 분석 기록**: 과거 분석을 날짜·카테고리 수·3색 집계와 함께 목록으로 제공하며, 클릭 시 결과를
  다시 열람한다.
- **내 공고 / 내 자소서**: 자주 쓰는 채용공고와 자소서(문항+답변 묶음)를 저장해 두고 재사용한다.
  분석 화면의 "불러오기" 드롭다운에서 선택하면 입력칸이 자동으로 채워진다.
- **저장·수정·삭제**: 저장 시 같은 이름이 이미 있으면 안내 후 **덮어쓰기(수정)** 하며, 마이페이지에서
  **이름 수정** 및 **삭제**가 가능하다.

> *(그림 삽입 위치) 마이페이지 / 분석 화면의 불러오기 드롭다운 스크린샷*

---

### 6. 회원 탈퇴 · 개인정보 보호

- 마이페이지에서 **회원 탈퇴**가 가능하며, 확인 후 Supabase에서 계정을 삭제한다. 이때 데이터베이스의
  **ON DELETE CASCADE** 설정에 의해 해당 사용자의 자소서·공고·분석 기록이 함께 삭제된다.
- 자소서는 민감한 개인정보이므로 **RLS(Row Level Security)** 로 보호하고, 백엔드는 service_role
  키로 접근하되 코드 수준에서 사용자 id를 직접 검증한다.
- 비로그인 분석 즉시 폐기, 프론트에는 anon 키만 노출, 서버 키·LLM 키는 백엔드 환경변수에만 보관한다.

> *(그림 삽입 위치) 회원 탈퇴 확인 다이얼로그 스크린샷*

### 7. UI / UX (라이트 · 다크 테마)

- **NANO 다크퍼플** 계열을 기본으로 하며, **라이트/다크 모드 토글**을 지원한다(흑백 아이콘,
  localStorage 저장, 시스템 설정 자동 감지, 렌더 전 적용으로 깜빡임 방지).
- 색상은 시맨틱 토큰(CSS 변수)으로 통일되어, 팔레트를 한 곳에서 관리하고 두 모드에서 일관되게
  동작한다.
- 입력 화면은 채용공고(공통)와 문항 반복 입력(최대 5개), **입력 글자수 표시**를 제공한다.
- 반응형 레이아웃과 자체 로고 마크를 적용하였다.

> *(그림 삽입 위치) 라이트/다크 모드 비교 스크린샷 2장*

### 8. 데이터베이스 설계 (Supabase / PostgreSQL)

| 테이블 | 주요 컬럼 | 설명 |
|---|---|---|
| `profiles` | id, email | Auth 사용자와 연결. 가입 시 트리거로 자동 생성 |
| `cover_letters` | id, user_id, title, **items(jsonb)** | 저장 자소서(문항+답변 묶음) |
| `job_postings` | id, user_id, title, content | 저장 공고 |
| `analyses` | id, user_id, **result_json(jsonb)** | 분석 결과 통째 저장 |

- 모든 사용자 데이터 테이블에 **RLS**를 적용하여 본인 데이터만 접근하도록 정책을 설정한다.
- `auth.users` 가입 시 `profiles` 행을 자동 생성하는 **트리거**를 둔다.

> *(그림 삽입 위치) Supabase 테이블 구조 / ERD 스크린샷*

### 9. 백엔드 API 명세

| 메서드 | 경로 | 설명 | 인증 |
|---|---|---|---|
| POST | `/api/analyze` | 분석 실행(+로그인 시 저장) | 선택 |
| GET | `/api/analyses/{id}` | 결과 조회(공유) | 불필요 |
| GET | `/api/analyses` | 내 분석 기록 목록 | 필요 |
| GET/POST/PATCH/DELETE | `/api/cover-letters` | 자소서 저장·조회·수정·삭제 | 필요 |
| GET/POST/PATCH/DELETE | `/api/job-postings` | 공고 저장·조회·수정·삭제 | 필요 |
| DELETE | `/api/account` | 회원 탈퇴 | 필요 |

- 입력 검증: 빈 입력 400, 문항 최대 5개 제한, 중복 이름 저장 방지(409).
- LLM/임베딩 실패 시 502로 명확한 오류를 반환하며, 프론트는 실제 사유를 표시한다.

### 10. 안정성 · 예외 처리

- **멀티 LLM 폴백 + 일시 오류 재시도**로 외부 API 장애에 대응한다.
- **응답 스키마 불변식 강제**로 LLM이 불완전한 값을 반환해도 결과 화면이 깨지지 않는다.
- **BGE-M3 모델은 서버 기동 시 1회만 로딩**(lifespan)하여 요청마다의 로딩 지연을 제거한다.
- Supabase 미설정·키 오류 등 환경 문제에도 서버가 기동되고 비로그인 분석은 정상 동작하도록
  지연 초기화(lazy) 및 폴백을 적용한다.

> *(그림 삽입 위치) 오류 발생 시 안내 메시지 / 콘솔 로그 스크린샷*
